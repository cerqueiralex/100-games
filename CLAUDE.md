It also covers the **profile color**: the catalogue is well-formed, Standard is the default, an unknown value is dropped by both `loadProfile` and `parseBackup` (while the rest of the profile survives), every color clears 3:1 on every theme with only its lightness moved, the chart ramps are real monotonic gradients that stay on the picked hue (with adjacent steps ≥0.075 lightness apart at the charts' 5-series cap, which is itself pinned), `applyProfileColor` fully clears itself when the player goes back to Standard, the hexes appear in no stylesheet, the frames are opt-in, the picker's grid has exactly one column per catalogue entry plus Standard (so it can never wrap), and no progression surface paints with the raw `--play-7`. It also proves the **card surface stays one rule** (`effects.css` must not repeat `.fx-card` behind a `[data-theme]` prefix; the theme difference lives in `--card-fill`/`--card-hairline`) — see DESIGN.md, that split once outranked every component override on the light theme. It also guards the **version stamp** (see Versioning below): `package.json`'s version must be well-formed MAJOR.MINOR.PATCH integers (a malformed one poisons the derived minor), the settings page must render `VERSION_LABEL` and must not hardcode a `vN.N` literal, and the deploy workflow must keep `fetch-depth: 0`. **Run this after any edit to `src/games/crossword/logic/puzzles.ts`, `src/games/arrow-crossword/logic/puzzles.ts`, `src/games/word-wheel/logic/levels.ts`, `src/games/cryptogram/logic/words.ts`, any generator/puzzle-bank/content file the validate payloads cover — and after adding a game or category (the landmark check is what keeps achievements in sync with the library).**

**`npm run validate` is deterministic**: it seeds `Math.random` at the top of `scripts/validate.ts` (`VALIDATE_SEED`, fixed default), because unseeded generator checks failed the gate on unlucky draws and blocked deploys with nothing broken. A red validate therefore means a real regression — never "fix" one by loosening a tolerance. To fuzz other draws deliberately: `VALIDATE_SEED=<n> npm run validate` (a failing seed reproduces exactly).

There is no test framework or linter; `npm run build` and `npm run validate` are the gates. The GitHub remote uses SSH (`git@github.com:cerqueiralex/100-games.git`) — the HTTPS URL has no credentials on this machine.

**Deployment**: the user plays the installed PWA on iPhone, so a change is DELIVERED only when it is pushed — a commit that stays local leaves the phone on the previous build (a whole chess engine once shipped that way and was reported as "not implemented"); finish shipping work with `git status -sb` showing no `[ahead N]`. Every push to `main` triggers `.github/workflows/deploy.yml`, which validates, builds with `VITE_BASE=/100-games/`, and deploys `dist/` straight to Pages via `upload-pages-artifact` + `deploy-pages` → live at https://cerqueiralex.github.io/100-games/ (the user plays the installed PWA from there on iPhone). Because of subpath hosting, in-app URLs must use `import.meta.env.BASE_URL`, never absolute `/` paths. Two settings are load-bearing and were configured by hand (the workflow token lacks admin rights, so `actions/configure-pages` must NOT be added): Settings → Pages → Source = "GitHub Actions", and the `github-pages` environment's deployment-branch policy must allow `main` — if deploy runs fail in seconds with "Branch main is not allowed to deploy", that policy is the cause. The old gh-pages-branch publisher route is dead (its deploy step times out); don't revive it. **The workflow's checkout MUST keep `fetch-depth: 0`** — the app's version number is the commit count, and the default shallow checkout would stamp every deploy `x.y.1` (see Versioning below).

**Versioning (the version is DERIVED from git — never hand-edited to ship)**: the version at the bottom of Settings is `MAJOR.MINOR.PATCH`, computed by `buildStamp()` in `vite.config.ts` and injected via `define: { __APP_BUILD__ }`; `src/platform/version.ts` is the only module that reads it (typed in `src/vite-env.d.ts`), exporting `VERSION_LABEL` (`-dev`/`-prod` channel suffix) and `buildLine()`. The parts:

- **MAJOR** — `package.json`'s major. The only editorial number: a redesign, or a change that breaks saved data. Judgement call, so a human/agent sets it deliberately.
- **MINOR** — `package.json`'s minor plus the `feat:` commits made **since that version line was last edited** (`git log -1 -G'^\s*"version":' -- package.json` anchors the range). So whatever you write in `package.json` is literally what the app shows on the next build, and each later `feat:` adds one. Never re-base the version in the same commit as a feature — the anchor is that commit, so its own `feat:` would not count.
- **PATCH** — the commit count, so every push mints a new version.

**THE COMMIT-SUBJECT RULE (load-bearing — this is the whole automation):** a commit that **launches a new game or any user-facing feature MUST be subject-prefixed `feat:`** (or `feat(scope):`, `feat!:`) — Conventional Commits. That prefix, and nothing else, is what raises MINOR. Everything else (fixes, polish, refactors, docs, content/QA work, build changes) uses any other subject and leaves MINOR alone; prefix those `fix:`/`chore:`/`docs:` or the repo's plain imperative style. Editing `package.json`'s version is how you deliberately re-base MAJOR.MINOR; it takes effect immediately because the feature count restarts from that commit. Audit with `git log -E --grep='^feat(\(.+\))?!?: '`.

Adding a game is therefore a `feat:` commit — with `npm run validate` proving the landmark catalogue re-derived (see the landmark sync rule), the same push also bumps MINOR. Consequence worth knowing: MINOR moves at the moment the commit lands, not when `package.json` is touched, so a feature and its version bump can never disagree.

**The stamp is computed once, when Vite loads its config** — a dev server left running would otherwise serve the version from whenever it started (this is exactly how Settings once showed a version matching neither `package.json` nor the commit count). The `restamp-on-git-change` plugin watches `.git/logs/HEAD` and `package.json` with `fs.watch` (Vite's own watcher ignores `**/.git/**`) and restarts the server, so dev always shows what a build right now would produce. Production builds always compute fresh.

`buildStamp()` also records the short sha (suffixed `+` when the tree is dirty, `-uno` so untracked scratch files like `backlog.txt` don't count) and the COMMIT date, so rebuilding a commit is byte-identical. Every git read falls back rather than throwing, so a build without `.git` still succeeds. Never hardcode a version string in a component — `npm run validate` fails on a literal `vN.N` in the settings page for exactly that reason.

## What this is

An offline-first PWA of classic puzzle games (React 18 + Vite + TypeScript, no backend, no router — navigation is component state in `App.tsx`). Seventy-one games so far: Sudoku, Crossword, Word Wheel, Memory Match, Simon, N-Back, Dual N-Back, Number Merge, Color Connect, Tic-Tac-Toe, Image Puzzle, Maze, Cryptogram, Minesweeper, Logic Puzzles, Battleship, House Puzzles, Nonograms, Killer Sudoku, Kakuro, Skyscrapers, Futoshiki, Binary Grid, Aquarium, Tents & Trees, Bridges, Slitherlink, Nurikabe, Lights Out, Fleet Finder, Code Breaker, 2048, Make 24, Target Number, Math Sprint, Magic Square, Sequence Cracker, MathDoku, Word Guess, Word Search, Word Ladder, Anagram Sprint, Missing Vowels, Hangman, Letter Hunt, Backwards Span, Number Trail, Pattern Recall, Moving Cups, Schulte Table, Stroop Match, Odd One Out, Count & Compare, Sokoban, Pipes, Gridlock, Tower of Hanoi, Tangram, Untangle, Laser Mirrors, Jigsaw, Peg Solitaire, Connect Four, Reversi, Checkers, Dots & Boxes, Klondike Solitaire, Chess, Arrow Crossword, Snake, Block Drop. All persistence is localStorage under versioned keys (`100games.v1.*`) via `src/platform/storage.ts` — game-specific extras (e.g. Logic Puzzles preset progress) go through its `readGameData`/`writeGameData` helpers so `resetAll` (which sweeps the whole `100games.v1.` prefix) always finds them; game code never touches `localStorage` directly. It is used on desktop browsers and installed on iPhone via Safari's Add to Home Screen (PWA config in `vite.config.ts`).

Backup export/import lives in `src/platform/backup.ts` (Settings → Data): `exportBackup()` writes one JSON file with settings + profile + history + progress, and `parseBackup()`/`applyBackup()` restore it on another device or from a friend. It sits above `storage.ts` and `progress/` (never the reverse — `storage.ts` must not import `backup.ts` or a cycle appears). **A backup file is UNTRUSTED input**: `parseBackup` validates every section field by field, drops malformed history rows instead of poisoning the log, clamps volume and rejects unknown theme values (a bad value must never brick theming; an `accent` from an older build is simply ignored), and returns a human-readable reason rather than throwing. It never writes — the UI previews the summary and the player confirms first, because import replaces what's on the device; sections missing from the file are left untouched. After `applyBackup`, call `AppState.reloadFromStorage()` so every store re-reads.

Play streaks and landmark trophies live in `src/platform/progress/progress.ts`, a separate store (`100games.v1.progress`) that is deliberately PERMANENT: it survives the 1000-entry history cap and Settings → Clear history (only "Reset everything" sweeps it), and a missing or stale-shaped store reseeds itself retroactively from history. Every result funnels through `AppState.recordResult` → `recordProgress`, which marks the local calendar day as played (any outcome counts), the game as played, and won difficulties, runs up the lifetime counters, then evaluates the landmark catalogue — first game, 9 streak tiers (7…365 days), a 50/100/200/500/1000 **plays** ladder, the same rungs for **clean wins**, a 10/25/50/75/100 ladder for **clean wins in a row**, six **rank crowns** (level 10/25/50/100/150/200), all-games-played, the five per-difficulty **Grand Slams** ("beat every game" on one tier), one mastery per non-empty category (an empty category must never get a landmark or it unlocks vacuously), the two cross-category trophies (**Renaissance** — a clean win in every category; **Full House** — one category swept on all five tiers), a dozen one-off **feats** (see below) and the games' own **easter eggs**. Unlocks are stamped once and never revoked.

The two volume ladders read `progress.plays` and `progress.cleanWins`, permanent counters that live in the store for the same reason personal bests do — history is capped at 1000 rows and clearable, so counting from it would make a 500-game trophy un-earnable. **`plays` counts FINISHED sessions only** (won or lost): an abandon is not a game played, exactly as it earns no play XP, and a trophy anyone can hold down a button for is worth nothing — the requirement line says "Finish N games" so the meter never promises credit it will refuse. A store written before either counter existed backfills once from history in `loadProgress` (never in `recordProgress` — see the XP backfill note below, same trap).

**Feats are MOMENTS, and a moment must be stamped, not recomputed.** `progress.feats` is a permanent list of one-off achievements that no state can reproduce after the fact: "won the very next game after a loss", "finished a game at 2am", "played every category in one day". `applyFeats` (inside the single `applyResult` write path) stamps them, and landmark evaluation stays a PURE function of `PlayerProgress` — which is what lets `loadProgress` re-evaluate the whole catalogue on every start. The consequences that keep them honest: (1) a feat-backed landmark unlocks from `p.feats`, never from its meter, so a meter is free to show something live and actionable (Genre Hopper shows *today's* categories, Deep Cut shows how much of the library you have tried) without ever taking a trophy back; (2) **only FINISHED sessions count** anywhere in `applyFeats` — an abandon earns nothing and breaks no clean-win run, for the same reason it is not a `play` — the one exception being that an abandon DOES count as a failed attempt for Third Time's the Charm, because walking out of a losing board is the story that trophy is about; (3) the two small-hours windows are disjoint (Night Owl 00:00–03:59, Early Bird 04:00–05:59) so one play can never pay out both; (4) speed trophies require `durationSec > 0` — a run the clock never started is unmeasured, not instant; (5) the comeback/obscurity feats are judged against the state BEFORE the result is folded in, which is why `applyFeats` runs first inside `applyResult`; (6) `progress.today` keeps only the CURRENT day's categories — a permanent store must not grow a row per calendar day. Feats earned outside a game (making a win card, sharing the app's link from Settings → Share the app, exporting or importing a backup) go through the second write path, `recordFeat` → `AppState.markFeat`, which stamps once, pays the usual landmark XP and returns `null` when the feat was already held; validate pins each out-of-game feat to the surface that stamps it. A store written before feats existed replays its history **forwards** (`seedFeats`, in `loadProgress`/`normalize` — never at write time) because a comeback only exists in the right order; history is stored newest-first. Feats arriving from a backup are sanitized by shape but an UNKNOWN feat id is deliberately KEPT — a file from a newer build must not have its trophies deleted by an older reader.

**Easter eggs are declared by the GAME, never by the platform** (`GameDefinition.easterEggs`): id, title, requirement, emoji, palette slot and a `when(result)` predicate. The catalogue spreads whatever the registry holds (`egg-<gameId>-<eggId>`), exactly as it spreads one mastery per non-empty category — the landmark sync rule holds, and progress logic still never learns a game id. Because the predicate is handed the `GameResult`, an egg can key off anything a result carries, including `GameResult.options` (the frozen setup-screen choices, recorded for exactly this reason): Memory Match's "Gotta Catch 'em All" is `outcome === 'won' && options?.theme === 'pokemon'`. A game's predicate runs inside everybody's write path, so it must be pure and cheap, and it is called inside a try/catch — one game's bug must never stop a result being recorded. Eggs are `secret: true`: hidden art, title and requirement until found (see DESIGN.md "Streak & landmarks"), and they live in their own "Easter eggs" section of the gallery. `npm run validate` re-proves the whole of the above through the real write path.

**Level landmarks force an ordering rule inside `awardXp`:** XP is added to `p.xp` as each award is granted, not summed at the end, and landmarks are evaluated **after** that in a loop — a crown is judged against the XP this very result just earned, and the 80 XP a landmark pays can itself carry the player over the next tier, which must then unlock in the same breath. `npm run validate` drives the real write path against an in-memory `localStorage` to re-prove exactly that (plus what each outcome counts as, and the backfill).

**Rank crowns** (`RANK_TIERS` in `progress/xp.ts`) are the one source for the level ladder: the profile's `RankLadder` row, the corner badge on the level card, the crown left of the home header's level chip, the six `level-*` landmarks and the share card all derive from it — never enumerate the tiers a second time. Their materials are fixed `--rank-*` tokens (see DESIGN.md "Rank crowns"), and validate asserts every tier has both its color tokens, that the landmark list matches the ladder in order, and that `rankForLevel` never hands out a crown one level early. The badge is **extruded and textured to look like its material** (wood grain, brushed iron, polished silver/gold, mirror platinum, gem-faceted challenger); that texture is SVG path data in ONE table, `design/rankMaterials.ts`, read by both the SVG badge (`RankCrown`) and the share card's canvas port (`drawRankCrown`, via `Path2D`) — they are two drawings of one crown, and validate fails if a rank loses its material or either renderer stops importing the table.

**The canvas share cards follow the player's appearance**: `cardTheme()` in `ShareCard.tsx` reads `--bg`/`--surface`/`--text`/`--accent`, and `drawCardChrome` returns the theme it painted with so no caller re-reads or hardcodes ink (they were once hardcoded black, which handed a light-theme player a card from a different app). Semantic colors — clean-win green, a landmark's `--play-*`, a rank's material — stay fixed across themes as everywhere else. See DESIGN.md "Share cards follow the player's theme". UI: `StreakChip` in the home header, `StreakHero` (Duolingo-style flame + week row) and `LandmarksSection` (trophy gallery + detail modal + shareable canvas card via ShareCard's `drawCardChrome`/`ShareImageModal`) at the top of the profile — see DESIGN.md "Streak & landmarks" for the locked/unlocked art rules. Landmarks have TWO surfaces with two jobs: that gallery is the CHECKLIST (whole catalogue, locked art, live meters), while `LandmarkBadges` — the row at the foot of the level card, reached through `LevelHero`'s `badges` slot rather than an import, which would close a Level↔Landmarks cycle — is the DISPLAY CASE: unlocked only, catalogue order, and nothing at all when nothing is earned. Never let the case grow locked plates or meters; validate enforces it. **Only a CLEAN win counts as beating a tier** (`countsAsBeaten` in progress.ts: won with zero hints and zero assists used — passive assists count as used whenever enabled). That one predicate gates the green ring, the star seal, the game trophy, the difficulty-sweep and category-mastery landmarks, and the "all difficulties" XP award, so every one of those marks means exactly one thing: unaided. A helped win still counts as a play, a streak day, XP and a history row — it just isn't a conquest. Never add a second path into `p.wins`; `npm run validate` re-proves the predicate against helped wins, losses, abandons and a mislabelled row. The same store drives the per-game **completion markers** via `beatenDifficulties`/`allDifficultiesBeaten`, one standard on every surface: a 3px green ring (semantic `--good`, never the accent — built as 1px border + 2px inset ring so state never changes geometry) plus the shared `.beat-seal` pinned top-left (green disc, gold `--warn` star, darker-green rim). Applied to the setup screen's difficulty picker and the profile's high-score tiles; a game beaten on all five tiers shows the `.game-card-trophy` badge (white flat `RosetteIcon` — the category-mastery medal shape, deliberately NOT a crown since crowns belong to the rank ladder — on an `--xp` orange disc, 3px darker-orange rim — a swept game wears the progression color, while single-tier seals stay green) on its home card and next to its name on the profile's high-score card. Two more surfaces COUNT those swept games, both from `allDifficultiesBeaten(progress, …)`: the profile's **"Game crowns" KPI** (scoped to the page's active filter, and labelled "Game crowns" rather than "Crowns" because the rank ladder on the same page has six crowns of its own) and the **`GameCrownBadge`** in the level card's top-LEFT corner — the counted form of the same mark, facing the rank crown on the right, lifetime total because that card is identity and doesn't move when the page below it is filtered. The badge shares `.game-card-trophy`'s material exactly (`--xp` disc, `--xp-rim` border, white rosette — the SAME `RosetteIcon` drawing on both surfaces; validate compares the two rules), taking the rank crown's 38px BOX — but the disc and the art inside it are derived from `RANK_BADGE`, not set to that box: `RankCrown` draws its disc at r=30 in a 64 viewBox and its crown at ~62% of that disc, so a plain 38px disc with art at 100% shipped ~7% wider with its jewels ~1px off the rim, and the two corners of one card visibly disagreed (validate now fails if either stops deriving). The count hangs off its bottom-right as a separate `.crown-badge-count` bubble in the SAME material — `--xp` fill, `--xp-rim` ring, extruded bottom edge, white ink — so the two read as one object. White is deliberate and taken with the contrast known (~3.5:1 on purple/blue, ~2.1:1 on the default orange, ~1.4:1 on yellow), so the digits are sized and weighted up; if a color ever reads badly, deepen the FILL to `--xp-deep` rather than darkening the ink, which is what would stop the bubble matching the badge. Validate proves that escape hatch clears 4:1 for every picker color on every theme. **The count never goes inside the art.** Three layouts that did (on the crown this mark used to be) all shipped and all failed: digits in its band (illegible), stacked under half-height art (silhouette destroyed), and overlaid across it (silhouette broken). Validate fails on any `<text>` in the badge art (`GameCrownBadge`/`RosetteIcon`). All five surfaces MUST read the progress store, never recompute from capped history, and any future surface reuses those same classes — see DESIGN.md "Completion markers".

**Daily Challenge** (`src/platform/daily/`) is one shared puzzle per local calendar day: the same game, tier and board for every player, with no server. Three rules hold it together:

- **The rotation is DERIVED, never enumerated.** `eligibleGames()` is `GAMES.filter(g => g.dailyChallenge?.eligible)`, and `assignmentFor(date)` is a pure function of the date and that list — a seeded shuffle per cycle (cycle length = eligible count) so every game comes up exactly once per cycle, plus one swap when a shuffle would repeat a game across a cycle boundary. Same discipline as the landmark catalogue.
- **An assignment is FROZEN the first time a day is seen.** `ensureTodayAssigned()` writes the record to `100games.v1.daily` on first sight, because the rotation depends on how many games are currently eligible: opting a game in or out shifts every *future* date (fine) but must never re-derive a date somebody already played. Imported backup records are authoritative for their own dates for the same reason.
- **A game only opts in when its board is fully determined by its generator at mount.** `dailyChallenge: { eligible: true }` in the definition is half of it; the other half is wrapping the board line in `withSeed(dailySeed, …)`. Games whose randomness continues during play (a tile spawning every move) or depends on the player's first move (**Minesweeper** lays its mines around the opening tap, so one seed still yields different boards) must NOT opt in — "the same board for everyone" would be a promise the game cannot keep.

Seeding works by swapping `Math.random` for a seeded stream around the single generation call (`withSeededRandom`, the technique `scripts/validate.ts` already used), never for the duration of play — a game's own randomness during a run must stay unseeded. **The callback must be synchronous**: an async one returns its promise at the first `await`, so the `finally` restores `Math.random` before the generator draws anything and every player silently gets a different board. `withSeededRandom` throws on a thenable rather than allowing that.

Daily runs go through the normal `GameShell` with `daily` set: the difficulty picker is replaced by the locked assignment, `dailySeed` reaches the game, and the save slot is mode-tagged (`GameSave.daily`) so a daily board can never be restored into an ordinary session. Completion is a WIN (a loss leaves the day open to retry) and is folded in *before* `recordResult`, so the XP award can see the streak it just extended. Only a same-day finish extends `streak.current`; a late one is still logged, shared and XP-paying — the same "counts as a play, not a conquest" logic as a helped win. The daily streak is deliberately separate from the play streak, with its own calendar-page art so the two trophies are never confused. `npm run validate` re-proves every eligible game is deterministic per seed (and that a *different* seed changes the board), the rotation's cycle coverage and no-adjacent-repeat rule, the streak predicate, that a hostile daily store is sanitized rather than trusted, and — through the real `recordProgress` write path — that every daily XP award is keyed to a state change (`firstCompletion`/`advanced`), so re-finishing a day pays nothing. The progress store keeps only the projections the trophies need (`dailyBest`, `dailyGames`), never the live streak: a permanent store must not hold a number that decays with the calendar. Consequence for the meters — `landmarkMeter` takes the live daily streak as an argument and shows it (what the player can act on, exactly like `streak.current` for play streaks), while UNLOCKING falls back to `dailyBest` so a trophy is never taken back.

**Player level & XP** live in the same permanent store (`progress.xp`, plus `progress.records` for personal bests); the rules and arithmetic are in `src/platform/progress/xp.ts`, which is deliberately **dependency-free** (no storage, no registry) so `progress.ts` can import it without a module cycle — level math never moves into a component. 100 XP per level (level 1 at 0 XP). Awards, granted inside `recordProgress` where "what just changed" is known: new calendar day 10, game played 10, personal record beaten 10, game swept on all five difficulties 80, landmark unlocked 80. **Every award is keyed to a state change** (a day is new once, a landmark unlocks once, a game is swept once), which is what makes a level un-farmable; abandoned sessions earn no play XP for the same reason (quitting takes two seconds), though they still count as a play day. `recordProgress` returns `{ progress, award }` and `AppState.recordResult` passes the `XpAward` back to `GameShell`, which shows `XpEarned` in the results modal and opens `LevelUpModal` *before* the results (same reasoning as the win celebration). **Personal bests live in the progress store, never in history** — history is capped and clearable, so reading records from it would re-pay the same record forever. A store written before levels existed is backfilled retroactively **in `loadProgress` and persisted there**, never in `recordProgress`: `recordResult` appends to history first, so a backfill at write time counts the new game twice and can swallow the level-up card. XP arriving from a backup file is untrusted — `normalizeProgress` clamps it to a finite non-negative integer and drops malformed records, and `npm run validate` re-proves the level boundaries, meter consistency and that clamping.

**Landmark sync rule (load-bearing): the catalogue must stay DERIVED, never enumerated.** `LANDMARKS` is computed from `GAMES` and `CATEGORIES` at module load, and `landmarkMeter`/unlock evaluation read the live registry — so adding a game automatically grows the Collector/difficulty-sweep totals (still-locked trophies simply need the new game too; already-earned ones keep their stamp), and the first game of a new category automatically creates its "{Category} Master" landmark. Never hardcode a game count, game list, or category list inside progress/landmark logic, and never special-case a landmark per game — that is what would silently desynchronize achievements from the library. The same rule covers **whole families**: the Daily Challenge trophies are spread into `LANDMARKS` only while `eligibleGames()` is non-empty, exactly as an empty category gets no mastery landmark — a trophy nobody could ever earn is worse than no trophy. `npm run validate`'s landmark-catalogue check enforces this on every run (totals == registry size, one mastery per non-empty category, none for empty ones, fresh profile fully locked), so **after adding a game, run `npm run validate` and the achievements are proven in sync — no manual landmark edit is ever needed** (the only sanctioned edits are intentional new landmark KINDS, which also get a validate assertion).

**Player avatars** (`src/platform/design/avatars.tsx`) are either an emoji or a Pokémon sprite, both stored in the SAME `Profile.emoji` string: a value prefixed `pokemon:<id>` is a sprite, anything else is an emoji. One field, not a second `avatarKind`, is what keeps every profile, backup file and history row written before sprites existed working untouched. Render one through `<Avatar value={...} />` — never `{profile.emoji}` directly — and note that `public/pokemon/` is an APP asset shared by the profile and Memory Match, not the game's private folder. The canvas share cards need the sprite DECODED before they draw (`drawImage` on a half-loaded image silently draws nothing), so both card modals `await loadAvatarSprite(...)` and `ShareImageModal.render` may return a promise; the text form is the fallback, because a card missing its picture beats a card that never renders. Validate proves each avatar's sprite exists and that an emoji is never mistaken for a sprite.

**Profile color** (`src/platform/design/profileColors.ts`) is the app's ONE color setting — five colors plus Standard, picked in Profile → Edit and stored on `Profile.color`. It is deliberately not the removed accent picker returning: `--accent` stays monochrome ink so no game tool moves, and what a profile color repaints is the player's own chrome — `--xp` (so the level ring, XP bar, streak flame, streak count, week-row discs and Daily card all move together), the three profile frames (home header card + both avatar plates, as a 4px extruded border), and the profile page's charts. **Standard is the default and a real choice**: `Profile.color` is `undefined` until somebody picks, `--xp` is `var(--profile, var(--play-7))`, and every painted rule hangs off `[data-profile-color]` — so an untouched profile is the app exactly as it shipped and a player can always get that back. The hexes live in that module and NOWHERE else: `applyProfileColor` is the only writer of `--profile`, no stylesheet may set it or branch on `[data-profile-color='x']`, and colors that reuse a `--play-*` value do so deliberately. `profileHex` nudges LIGHTNESS only (never hue/saturation) until a color clears 3:1 against the theme background (yellow is 1.3:1 on warm paper; a deep teal that briefly shipped was 1.9:1 on black, which is why the lift branch exists and is proven on a raw hex through `legibleOn`). The picker is ONE row — `.color-row` is a fixed `repeat(N+1, minmax(0, 1fr))` grid that squeezes rather than wraps, and validate derives that column count from the catalogue, so adding a color without widening the grid fails instead of silently costing a row of modal height. `chartRamp` derives the chart series as a MONOTONIC light→dark gradient with a tight ±9° hue sweep; never interleave it (it reads as two alternating colors) or widen the sweep (yellow walks out to tan and lime). And never paint a progression surface with the raw `--play-7` — it resolves to the same orange today, which is exactly why four of them stayed literal and turned up orange beside a green flame. Untrusted input is sanitized in both `loadProfile` and `parseBackup`. See DESIGN.md "Profile color"; `npm run validate` re-proves all of it.

**Memory Match card themes** (`src/games/memory-match/logic/`) are three face sets behind one `GameDefinition.options` entry: Classic (emoji), Pokémon and Card deck (a Zodiac pixel theme shipped once and was removed — a save dealt from a removed theme is treated as no save by `MemoryMatchGame`, because its deck is face ids no remaining theme can draw). The deck stored in a save is a list of face IDS, never art, so a snapshot survives a redesign — and the classic theme's ids ARE its emoji, which is why saves written before themes existed still resume. **Every theme must supply at least 28 distinct faces** (the extreme tier's pair count): with fewer, a board deals the same face four times and either card of one pair "matches" either card of the other, which is unwinnable as the player sees it. Validate re-proves the count, deals real extreme boards, and rejects two faces that draw the same picture. Pokémon uses PokéAPI's Generation V sprites vendored under `public/pokemon/<id>.png` — **trimmed to their artwork bounds**, because each 96×96 sprite ships its own transparent padding and `object-fit: contain` otherwise drew Diglett at a third of Nidoking. Cards are hand-authored pixel art (`pixelArt.tsx` renders rows of palette characters as one path per colour) drawn as GLYPHS a pixel grid can hold — at 16px pictorial art was unrecognisable, and on a memory board "can't tell two cards apart" is a bug.

Content notes: Word Wheel levels (`src/games/word-wheel/logic/levels.ts`) and the Cryptogram word bank + hidden answers (`src/games/cryptogram/logic/words.ts`; puzzles are assembled at runtime by `generateCryptoPuzzle`, letters disguised behind shuffled pictograms from `design/icons.tsx`) are hand-authored and covered by `npm run validate`, like crossword puzzles. Logic Puzzles (`src/games/logic-grid/`) has a propagation solver whose invariant everything relies on: a clue set is only accepted when sound deduction alone fully decides the grid — which proves both uniqueness and guess-free solvability. Its 25 presets are original content derived deterministically from baked seeds (`logic/presets.ts`) and re-verified by `npm run validate`; the theme bank (`logic/themes.ts`) is original too — never copy puzzles from other sites. House Puzzles (`src/games/house-puzzles/`) reuses the same guess-free invariant with a positional solver: houses in a row, ordering clues (at/adjacent/direct/somewhere/between), seeded generation re-verified by `npm run validate`; its category bank (`logic/themes.ts`) is original content. Color Connect and Maze generate levels at runtime with guaranteed solvability. Image Puzzle loads photos listed in `public/puzzles/manifest.json` — users add custom photos by dropping a file there and listing it in the manifest. Drag-driven games (Number Merge, Color Connect) use pointer events with `touch-action: none` and rect-math cell hit-testing, not `elementFromPoint`.

`backlog.txt` at the repo root is the user's personal scratch file — leave it untracked and don't delete it.

`QA-LEDGER.md` at the repo root is the institutional memory of past bugs: one entry per mistake class (symptom, root cause, the rule that now prevents it). **Read it before non-trivial work** — its "Promoted" entries explain why certain rules are load-bearing, and its "Watch items" are recurring pitfalls to avoid. When you find or fix a real bug, run it through the promotion ladder in `.claude/skills/qa-everything/SKILL.md` (validate check → DESIGN.md/CLAUDE.md rule → platform component → ledger watch item) and update the ledger; it is versioned and commits with the code.

## Architecture: platform vs. games

The core invariant: **games live in isolated folders under `src/games/<id>/`; everything shared lives in `src/platform/`**. Games never import from each other (small helpers are duplicated rather than shared across game folders).

A game plugs in by exporting a `GameDefinition` (see `src/platform/types.ts`) from its `index.ts` and being added to the list in `src/platform/registry.ts`. That's the entire integration surface — the landmark/achievement catalogue derives from the registry automatically (see the landmark sync rule above; run `npm run validate` after adding a game to prove it). `GameDefinition.category` is required and must come from the fixed vocabulary in `src/platform/categories.ts` (logic/words/memory/focus/numbers/spatial/strategy/reflex) — the home filter chips, card tags and profile category statistics all derive from it; if a future game truly fits none, add ONE entry there plus the `CategoryId` union, never a per-game string. `GameDefinition.easterEggs` is the optional hidden-trophy contract (see the easter-egg rule above). `GameDefinition.options` is the OPTIONAL pick-one contract: a game contributes settings to its own setup screen (Memory Match's card theme is the first), each choice may carry a preview `icon`, the pick persists per game in `settings.gameOptions` and reaches the game as `GameProps.options`. An option is deliberately **not** an assist — it changes what the board is made of, costs nothing, and must never make a win "helped"; it is frozen at `start()` and stored on the save (`GameSave.options`), because a deck built from one theme cannot be drawn with another. `npm run validate` proves every option's default names a real choice.

`GameDefinition.tutorial` is required: every game ships an illustrated how-to-play as `tutorial.tsx` in its folder (3–6 `TutorialStep`s whose art composes the `.tut-*` CSS primitives — see the Tutorials section of DESIGN.md). `GameDefinition.mastery` is also required: every game ships an in-depth strategy guide as `mastery.ts` (origins/history, 4–6 strategy sections each with a data-driven MasteryArt illustration, emoji-marked bullets, 2–4 stable reference links — see DESIGN.md "Mastery guides"); the shell shows it as a "How to master" button under "How to play" on the setup screen. The shell surfaces it on the setup screen and via the header help button. The platform's `GameShell` (`src/platform/components/GameShell.tsx`) then provides for free: difficulty selection (five tiers: easy/medium/hard/pro/extreme — every game must supply configs for all five; `Record<Difficulty, …>` maps make the compiler enforce it), assist toggles (per SESSION — every assist starts off for each new game and nothing is remembered between games; see Assist/help tracking), the timer (games with their own pre-game picker, like Logic Puzzles' mode menu, call `holdClock(true)` so the clock only starts at real play), pause (the board hides on real pause only — finished boards stay visible for review), restart and the two header exits — **back** to this game's setup screen and **home** to the game list, both through the same `leave(to, recordAbandon)` path so either is recorded as `abandoned` unless the game finished or was saved (see DESIGN.md "Leaving a game") — save & resume, the tutorial entry points, result recording, the standard win celebration, the closable completion modal with a "Show results" reopen pill, and the shareable win card.

**Win celebration (platform-owned, never per-game):** on `outcome: 'won'` the shell sets `celebrating`, renders `WinCelebration` (`WIN_CELEBRATION_MS`, currently 3.5s — the CSS keyframes are pinned to it) and gates the results modal on `!celebrating`, so the player sees the board they just finished before any statistics appear. The layer is `pointer-events: none` with an edge-only radial glow — it must never cover or tint the board (that was the original bug: the modal cut off each game's own payoff animation, e.g. Pipes' water reaching the last tile, which reads as failure). Games need no cooperation and must NOT delay `onFinish` or roll their own win animation — see DESIGN.md "Win celebration". Losses open the modal immediately.

The home header is one `.fx-card` (greeting + player name, streak pill, avatar; the two right-hand controls share a `--head-token` height so they can't drift) and the WHOLE card is one shortcut to the Profile tab (`HomePage.onOpenProfile` → `setTab('profile')` in `App.tsx`; a `div[role=button]` because a `<button>` may not contain the `<h1>`/`<p>`, pressing like a game card via paint + transform only so the 4px profile frame never moves) — never put a second interactive control inside it, and the category filter is a single sideways-scrolling row with edge fades and arrow controls — see DESIGN.md "Horizontal scrollers" before building another one. Directly under it sits **Last played**: the 3 most recently played games as one row of three shortcut pills, newest on the left, deduped by game (replaying one game must not fill the row with it) and derived from `history` — hidden while a search or category filter is active, since the page is then a result list. It shares the category chips' `--home-chip-h` height token so the two rows can never drift apart (DESIGN.md "Pill rows share ONE height token").

**Browsing state lives in `App.tsx`, not `HomePage`:** the home list's search text, category filter and scroll offset survive a game visit (`listScroll` captured on open, restored in a `useLayoutEffect`; entering a game scrolls to top). `HomePage` unmounts while playing, so anything that must survive the round trip belongs in `Shell` — returning from game #40 must never dump the player back at the top of a 71-game list.

Data flows one way: the shell passes `GameProps` down (`difficulty`, `assists`, `paused`, `elapsedSec`, `onToggleAssist`, plus `savedState`/`registerSnapshot` for save-resume); the game reports upward through `events.onStats(...)` (continuously, so abandons capture the latest state) and `events.onFinish(...)` (exactly once — games guard with a `done` ref). Games generate their board in a `useMemo`; the shell remounts them via a `key` to start a new game.

Save & resume is mandatory per game (see DESIGN.md "Save & resume"): register a JSON-serializable snapshot provider in a dependency-less effect, and hydrate every initializer from `savedState` when present. The shell stores one save per game (`100games.v1.saves`), shows the Continue card on setup, restores elapsed time, and deletes the save when its session finishes. A game whose snapshot can return `null` (a pre-game menu: Maze's size picker, Battleship's fleet placement, the vs-Robot menus) MUST also `holdClock(true)` there — that is what disables the header Save button, and without it the player taps an enabled button that silently does nothing. The save is also mode-tagged (`GameSave.daily`) and only offered back in the mode that created it.

### Assist/help tracking (user-mandated, preserve it)

Every game result stores both `assistsEnabled` and `assistsUsed`; `cleanWin` = won with zero hints and zero assists used. Convention: **passive** assists (highlights, auto-check, slow pace) are added to `assistsUsed` whenever enabled — including when toggled on mid-game; **active** assists (hint/peek/reveal/replay buttons) are added on use and usually also increment `hintsUsed`. History and statistics distinguish clean wins from assisted wins everywhere — new features must not blur this.

**Every assist starts OFF, in every game, every time — and a toggle is never persisted.** Because a passive assist counts as used the moment it is on, an assist that started on (145 of the 200 toggles once shipped `defaultOn: true`, and any toggle was then remembered per game in `settings.gameAssists`) silently turned unaided wins into helped ones — no green star, no trophy, no clean-win run, for a player who never asked for help. So `AssistFeature` has no default field at all, `PlatformSettings` has no `gameAssists`, and the toggles are `GameShell` state (`freshAssists`) that resets whenever the setup screen shows — a restart or "play again" inside one sitting keeps them, because the player never went back to the screen where they are chosen. The ONE place a toggle persists is `GameSave.assists`, written with the save and restored on Continue, so a resumed run keeps its passive assists working and its helped verdict cannot drift (every game's own snapshot also carries `assistsUsed`, which is what actually decides the verdict). A store from an older build hands its per-game toggles to the saves that lack their own once, in `loadSettings`, then drops the field; a backup file's `gameAssists` is ignored. `npm run validate` fails on a `defaultOn`, a settings field, a shell that resolves assists from settings, a save that stops carrying them, or a setup screen that stops resetting them.

**Errors measure answers, not touch accuracy.** A keystroke must never be charged as an error on its own: errors are counted when the player asks for a check (a Check button) or, per keystroke, only under an opt-in real-time check assist — and a full-but-wrong board is feedback (a toast), never a penalty. Crossword's Auto-check once shipped default-ON and charged every wrong letter as typed, so a mis-tap on the compact keyboard scored as a wrong answer, and its "grid is full" branch charged every further keystroke while the player hunted the typo. Errors are a statistic (score penalty, results line), never help: `cleanWin` reads only `hintsUsed` and `assistsUsed`.

## Design system (mandatory)

`src/platform/design/DESIGN.md` is the rulebook for ALL UI work; the user has explicitly required it be followed. The load-bearing rules:

- Colors only via tokens in `design/tokens.css`. The palette is **monochrome ink plus one**: `--accent` (white; near-black on the light theme) paints every tool in every game, and `--xp` (orange) is the single secondary color, reserved for progression (level/XP/streak). Only `data-theme` (black/dim/light) is an attribute on `<html>`, set by `AppState`. The six-way accent picker was REMOVED — it multiplied the surface to check for one bit of taste; don't reintroduce a color setting. Semantic colors (`--good`, `--bad`, `--warn`, `--xp`) are fixed.
- Surfaces are **flat with NO gradients**, defined once in `design/effects.css` and bound both to `.fx-card` and to every shared card-component class listed there — component CSS never declares its own card background/border (this is what keeps Settings etc. in sync with redesigns). That rule is **one rule for all three themes**: themes differ only through `--card-fill`/`--card-hairline` in `tokens.css`, and it must never be repeated behind a `:root[data-theme='…']` prefix — the light copy sat at specificity (0,3,0) and silently outranked every deliberate component override (the Daily card's `--xp` ring, the selected appearance button, the dropdown focus border) on the one theme least likely to be checked. Validate-enforced. The depth standard is the **extruded "candy/pushable" style**: flat fills with a darker inset bottom edge (`box-shadow: inset 0 -3/4px 0 var(--edge)`, token per theme; solid colored fills use `rgba(0,0,0,~0.25)` instead) on cards, buttons, and gap-separated game tiles. Buttons press DOWN: `:active` = `translateY(2px)` + edge shrinks to 1px — but never add a press transform to elements positioned via inline transforms (e.g. Word Wheel letters). NO drop shadows on resting surfaces (floating overlays like modals/pills keep `var(--shadow)` for elevation), no specular edges, no 3D tilt. Deliberate flat opt-outs: home search bar, in-game info strip, continuous boards (sudoku/crossword/logic-grid cells).
- Charts (profile page) are dependency-free SVG components in `platform/components/charts.tsx`, colored per game from the `--play-*` content palette (via the chart-safe slot list in `charts.tsx` — never `--play-9`, which is white). **Every profile chart caps at 5 series** (`MAX_SERIES`, validate-pinned), folding the tail into one grey "Other" — more series made the legends unscannable and put a profile-color ramp's neighbouring steps too close to tell apart.
- Tile boards must keep stable geometry (DESIGN.md "Tile grids"): pin both grid axes (`grid-auto-rows: 1fr` or `aspect-ratio` on the tile), and tile state/press styles may change paint only (colors, transform) — never border-width, padding, or font-size.
- Icons only from `design/icons.tsx` — monochrome SVG, `currentColor`. **No emojis in UI controls** (emojis are fine as game content, e.g. memory-card faces, and celebratory content). Game identity icons are the one exception: colorful sticker-style SVGs in `design/gameIcons.tsx` (keyed by game id, fixed own palette, documented token opt-out) shown on the home cards — a new game adds its sticker there.
- In-game toolbars are rows of `PadTool` buttons (`platform/components/ui`) in equal-width grids (`grid-auto-flow: column; grid-auto-columns: minmax(0, 1fr)` — tracks may shrink so long label rows never overflow the phone viewport). `PadTool` is the standard for every game tool: accent-tinted with hover/press effects and a built-in click sound (`silent` prop when the handler plays its own sfx, `active` for toggles) — never hand-write `<button className="pad-tool">`. On-screen QWERTY keyboards are the shared `Keyboard` component from the same module (one `.kbd` CSS block, per-letter state via `keyClass`, wide Enter/⌫ via `bottomLeft`/`bottomRight`) — see DESIGN.md "Keyboard"; users: Hangman, Word Guess, Word Ladder, Crossword, Arrow Crossword, Cryptogram.
- **Bottom menu is ONE card**: every game puts ALL its bottom controls — tool rows AND any input surface (keyboard/d-pad/digit pad) — inside a single `.game-tools fx-card`, never sibling panels. It docks to the viewport bottom (`position: sticky`) so controls stay reachable while a tall board scrolls behind it; as a floating overlay it carries `var(--shadow)` and sits at `z-index: 30` — the pause overlay (z 40) and all modals/pills layer above it. A game with no tools (or whose tools are all assist-gated off) renders no card at all. On phone widths (`max-width: 700px`) the card must stay around a third of the viewport or less so the board keeps the screen: oversized content compacts (Word Wheel's wheel) or scrolls internally (Logic Puzzles' clue list) — see DESIGN.md.
- All CSS lives in `src/styles/global.css` (game sections are marked); tokens/themes live in `design/tokens.css`, imported at its top.

## Game content notes

- Sudoku puzzles are generated at runtime with a uniqueness-guaranteeing solver (`src/games/sudoku/logic/generator.ts`).
- Crossword puzzles are hand-authored coordinate/word lists; the engine derives and validates the grid. `validatePuzzle` rejects mismatched intersections and any letter run without a matching entry — this is what `npm run validate` runs.
- **Arrow Crossword** (`src/games/arrow-crossword/`, the Scandinavian/arrowword variant) keeps the clue INSIDE the grid: a clue cell carries up to two short texts with arrowheads, the `right` answer starts in the cell beside it and the `down` answer in the cell below, and there is no numbering or clue list — the only other surface is the readout above the keyboard, which magnifies the clue of the answer you are on. The author format is the Crossword's (entries positioned by their FIRST letter, in `logic/puzzles.ts` as `[answer, row, col, dir]` tuples); the engine derives the clue cell one step before each answer, lets one cell host a `right` and a `down` clue, and turns every unused cell into `empty` (drawn as page background, which is what gives the board its notched newspaper silhouette). Clues live in ONE alphabetical `CLUES` bank (answer → clue) so a word recurring across puzzles is clued once; they are deliberately terse because they are printed inside a cell — 30 characters in a cell with one clue, 20 each when two share a cell (`CLUE_MAX_SINGLE`/`CLUE_MAX_DOUBLE`, validate-enforced). The GRIDS are laid out by `scripts/bake-arrowword.ts` (`npx tsx scripts/bake-arrowword.ts <tier> [count] [seed] [attempts] [budget] [ban] [used]` — row by row, every column held to a feasible prefix of a real word from the app's own word banks, every result proven by `validateArrowPuzzle`, printed as paste-ready tuples) and hand-picked; the clues are hand-written, and `validateArrowPuzzle` simulates their wrap (`clueLines`: words and hyphen halves, no segment longer than a line, four lines in a cell with one clue and two per half in a shared cell) because the print scales with the cell and a clue that fits a 60px easy cell can break mid-word at the 34px extreme floor. Tiers grow through rows more than columns (6×7 → 10×13) because a column costs cell width on a phone and rows only scroll; the board sizes its print with container units (`100cqw / --cols`) so every tier keeps the same letter-to-cell proportion, keeps a 34px cell floor and scrolls sideways inside `.ac-scroll` only on phones narrower than that. Same assist set and error discipline as Crossword (typing never charges an error; Auto-check is the opt-in per-keystroke check).
- Timed/sequence games (Simon, N-Back, Dual N-Back) drive trials with timeout chains inside effects keyed on `paused` — pausing clears timers and resuming replays the current sequence/trial rather than resuming mid-flight. Battleship's enemy turn uses the same pattern, and its AI is deliberately stateless (each shot is derived from the visible board in `logic/ai.ts`), which is what makes save/resume free.
- The new deduction puzzles (Nonograms, Binary Grid, Skyscrapers, Futoshiki, Kakuro, MathDoku, Killer Sudoku, Tents & Trees, Aquarium, Bridges/hashi, Slitherlink, Nurikabe, Fleet Finder) all reuse Logic/House Puzzles' guess-free invariant: each ships a propagation solver (Nonograms is a line-solver; Fleet Finder's is `logic/solver.ts`'s `propagateFix`) and its seeded generator only accepts a board that sound deduction alone fully decides — which proves both uniqueness and guess-free solvability. `npm run validate` re-proves every tier; never author or ship a board the solver can't decide.
- Nurikabe's board is drawn as a little floating world — raised grass blocks on a dirt side, water with drifting wave marks and foam along every shore, sand where nothing is decided — in fixed game-content colours (`--nur-*` on `.nurikabe`, the Reversi-felt/Gridlock-asphalt opt-out; the undecided sand alone is mixed with `--surface`). The game keeps the continuous drag-painted grid and paints the 2.5D inside each cell: neighbour-derived classes (`sn` dirt side where nothing stands south, `rn/re/rw` exposed sides, `ctl/ctr/cbr/cbl` corners that round because both their sides are exposed) so blocks fuse into one rounded island — the white foam is a rounded plate the LAND cell draws behind its block (`::before`, reaching 3px past every exposed side), never straight lines on the water cells, which cannot follow a rounded corner — and per-cell scenery (trees/rocks/tufts, grass shade, mirroring) hashed from the cell index and `puzzle.seed` so it is stable across renders, resumes and daily players — never `Math.random` at render. Numbered cells only get low scenery so the number stays legible.
- Lights Out ships an **exact** GF(2) minimal-press par: Gauss–Jordan over the toggle matrix (minimum-weight null-space search where the matrix is singular — 4×4 nullity 4, 5×5 nullity 2). It is computed live per state (sub-ms), drives the scoring par and the par-meter/hint assists, and must stay exact — no approximate press counts.
- Gridlock (Rush Hour) ships a **pre-baked, BFS-verified puzzle bank** (`src/games/gridlock/logic/puzzles.ts`, banded by tier) picked deterministically by seed; live full-component BFS is tens of seconds on hard tiers and would freeze the `useMemo`, so the bank MUST stay baked (regenerate offline via the bake harness, never hand-edit). Sokoban instead guarantees solvability by **reverse-pull construction** (pull crates from the solved state; the flipped move list is a legal forward solution) and sets par with a push-optimal A*.
- Tower of Hanoi computes par with **Frame–Stewart** DP on the 4-peg extreme tier (the `2^n−1` closed form only holds for 3 pegs); its hint is a BFS over the (tiny) state graph so it returns the true best move from any position, not a from-start replay.
- Strategy games (Connect Four, Reversi, Checkers, Dots & Boxes) are **minimax + alpha-beta** vs-AI on fast numeric board cores, and reuse Tic-Tac-Toe's vs-Robot / vs-Friend (pass-and-play) shape: best-of-N rounds, sudden death, `holdClock(true)` on the pre-game menu, and `hideStats`/headline/subline result presentation for local-multiplayer wins. **Chess** is the exception in that family: a single full game as White vs the robot, no pre-game menu (so no `holdClock` and the snapshot is always live). Its 0x88 engine (`src/games/chess/logic/engine.ts`) implements complete legality — castling, en passant, promotion, check/mate, stalemate, fifty-move, threefold repetition, insufficient material — plus FEN both ways and UCI move resolution, and **`npm run validate` proves it with exact perft counts** on the classic torture positions plus SAN and status spot-checks; never loosen a red perft expectation. **The robot is Stockfish** (`logic/engineClient.ts` + `public/stockfish/`): the published Stockfish.js 18 *lite single-thread* build (GPLv3, ~7 MB, no `SharedArrayBuffer`, so it runs on GitHub Pages without special headers) shipped UNMODIFIED as a separate program — loaded as its own Web Worker on demand (the Stockfish.js file *is* the worker script and resolves its `.wasm` beside itself, which is why there is no wrapper worker), spoken to over UCI text lines, never imported or bundled (that separation is what keeps the rest of the app off the GPL), and credited with its license file from Settings → About. **The five tiers are REAL strengths**, mapped in `logic/difficulty.ts` (`TIERS`, dependency-free so validate imports it): easy ≈300 Elo is an engine-free weighted lottery over the legal moves (captures favoured, walking into a free capture shunned — modern Stockfish cannot play that badly on purpose, its `UCI_Elo` floor is ~1320); medium ≈750 and hard ≈1200 inject error ON TOP of the engine — a shallow `go depth … movetime …` asked for `MultiPV` lines, then a lottery weighted toward the worse ones, capped by `maxDrop` centipawns so a robot may concede a pawn but never walks past its own mate in one; medium additionally rolls a per-move `blunder` (0.15: the move goes to easy's beginner lottery instead of the engine), because MultiPV alone can NEVER hang a piece — the engine's four best lines are its four best moves — and a 750 that never blunders reads as 1300; pro ≈1600 is the engine's own `UCI_LimitStrength`/`UCI_Elo`; extreme is full strength on a 1.2 s budget. **The ladder is CALIBRATED BY MATCHES, not by its table**: `npx tsx scripts/chess-ladder.ts ladder` (also `probes`, `match A B N`; `PLAN_<tier>='{json}'` overrides a tier for a run) drives the real modules and the real engine as a UCI child process against Stockfish's own `UCI_Elo` limiter as the yardstick — the shape it must reproduce is in that file's header (medium 0/6 vs 1320, hard 2/8 vs 1320 and 6/6 vs medium, extreme 4/4 vs 2000). What it taught: the tail weights are the strongest knob (two lines at depth 2 beat 1320 8–0; four tail-weighted lines at depth 2 score 2/8), depth 3 already beats pro, a small blunder rate on hard changes nothing measurable. Re-run it after touching `TIERS`. **Which of the engine's two answers a tier plays is decided in ONE place, `robotPick`**: with the strength limiter on, Stockfish's `info … pv` lines keep showing its FULL-STRENGTH move and only the `bestmove` token carries the weakened pick (measured: at 1600 the pv said f6e4, bestmove d7d5), so a one-line tier (pro, extreme, the Hint) plays `bestmove` and only the error-injection tiers rank the MultiPV lines — the client once ranked lines for every tier and pro silently played as extreme; validate pins it. The weights/drops are the tuning knob; validate pins the ladder's ORDER on every axis (movetime, depth, probability of the best line, allowed drop, Elo limit) so no tier can be configured weaker than the one below it. Rules never come from the engine: every engine move resolves through `moveFromUci` against the perft-proven generator, and a move that fails to resolve is answered by the built-in robot with a console warning, never applied. **That built-in robot (`logic/ai.ts`) is the fallback and must itself play chess**: its root loop once searched every move with an alpha-beta window, and since a fail-hard search returns bounds, every move "no better than the first" tied the best exactly and the slack filter picked at random — at every tier (extreme lost to the 300-Elo lottery); the root now searches each move with a FULL window, and validate probes it on mates and a hanging queen. Robustness rules: every `go` carries a `movetime` ceiling plus a watchdog (`stop`, then terminate → the game falls back); pause, undo and leaving `stop()` the running search (a cancelled search is ignored and the effect re-runs from the current position on resume, so a reply can never land on the wrong board); loading shows the download meter the loader reports over a MessagePort and fails LOUDLY after 30 s of silence — a card with "Try again" / "Built-in robot" (the old negamax in `logic/ai.ts` stays as that fallback, and as the Hint's). The **Hint** assist is the engine at full strength whatever tier the robot plays (active: `hintsUsed` + `assistsUsed`, blue wash on the two squares). The engine is NOT precached — installing must stay light and 68 games never need it — but `vite.config.ts` runtime-caches `public/stockfish/` on first use (CacheFirst; the file names carry the engine version, so RENAMING is how a new build invalidates the cache — never swap the binary under the same name) and denylists that path from the SPA navigate fallback so the license link opens as text. Chess never joins the Daily Challenge: the variance is the opponent, not the board. Validate re-proves all of it — ladder order, the lottery math and the mate guard, easy's legality and capture bias, FEN/UCI round trips, that the shipped files are whole (wasm magic, size) and licensed and credited, the worker/`BASE_URL`/PWA rules — and drives the real shipped files through `uci`/`isready`/`go` under Node. Draws are recorded as `outcome: 'lost'` with a "Draw" headline so a forced stalemate can never farm clean wins.
- **The Reflex games (Snake, Block Drop) are real-time canvas games.** Each board is ONE `<canvas>` at 100% of the game column (`aspect-ratio` in CSS, pixel size × devicePixelRatio from a `ResizeObserver`), redrawn every frame from a `requestAnimationFrame` loop that ticks the rules by accumulated time and stops on pause, on `document.hidden` and on unmount (resume restarts from the same position). Live state lives in refs — the loop mutates it 60× a second — and React state carries only what the HUD prints. The drawing follows the app's look without touching DOM styling: colours are the design tokens read through `getComputedStyle` (`--play-*` content palette, `--surface`, `--edge`, …), re-read on a `data-theme` change, and every element is the extruded 2.5D block the rest of the app uses (a face on a darker underside band). Snake glides by interpolating every segment from its previous cell by how far into the tick the frame is (`prev` body + `acc`), Block Drop animates flash → collapse on clears and a trail on hard drops; both play `sfx` on every meaningful action (new sounds: `crunch`, `tick`, `thud`, `clear`). Rules are dependency-free modules (`logic/engine.ts`) that validate drives: Snake's step/eat/wall/wrap/self rules and tier ordering (board size, speed, apple target), Block Drop's SRS rotation states and kick tables, the 7-bag, line clearing, spawn/lock-out and tier ordering (gravity, line target). Neither joins the Daily Challenge — their randomness continues during play (apples land, bags are drawn). Both queue/repeat input like a console game: Snake buffers up to three turns (never a reversal), Block Drop has DAS/ARR on held left/right (keys AND the on-screen buttons, which own the pointer), soft drop while Down is held, hard drop, a lock delay that moves and turns reset a few times, hold, a three-piece preview and a ghost; touch on the well drags a cell per cell, taps to turn, flicks down to drop.
- Klondike and Peg Solitaire ship **baked winnable/solvable start banks** because their DFS solvers are too slow to run at mount: Klondike draws easy/medium from a proven-winnable seed bank (harder tiers use random deals + unlimited undo), Peg Solitaire's pro/extreme starts come from solver-verified lists. Jigsaw reuses the Image Puzzle photo manifest (`public/puzzles/manifest.json`) via `import.meta.env.BASE_URL` through its own loader (no cross-game import), with a `--play-*` gradient fallback when a photo 404s.

## Verification workflow used here

UI changes are verified by running the dev server and driving the app with `puppeteer-core` (already a devDependency; connect with `browserURL`, no browser download) against the host machine's headless Chrome (`host-spawn google-chrome --headless --remote-debugging-port=9222 --user-data-dir=/tmp/... about:blank`). The sandbox's `/tmp` is not shared with the host — write screenshots to a path under `$HOME`. Games pick puzzles with `Math.random`; stub it via `page.evaluateOnNewDocument` when a deterministic board is needed (e.g. auto-solving a crossword to reach the win screen).
